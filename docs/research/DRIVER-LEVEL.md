# 驱动级虚拟显示器：可行性与方案

> 结论先说：**能做，但自己写驱动对当前目标没有额外收益。装现成签名驱动是更优解。**

## 一、什么是"驱动级"

普通程序**无法**在 Windows 里创建显示器。显示器在系统里是一个 PnP 设备，必须由**内核态显示驱动**注册。

微软从 Win10 1803 起提供了 **IDD（Indirect Display Driver）** 框架，让第三方用相对简单的方式写虚拟显示器驱动：

```
应用层            IDD 驱动（内核）              Windows
  │                    │                         │
  │  提供画面帧  ───►  IddCxSwapChain          Desktop Window Manager
  │  （共享纹理）      ├─ 上报 EDID/分辨率  ──►  识别为一块显示器
  │                    └─ 接收 DWM 渲染结果
```

关键 API：`IddCxAdapterInitAsync` / `IddCxMonitorCreate` / `IddCxSwapChainReleaseAndAcquireBuffer`

## 二、本机环境差距

| 项 | 要求 | 当前 | 差距 |
|---|---|---|---|
| Windows 版本 | Win10 1803+ | **Win11 build 26200** | ✅ 满足 |
| IDD 框架 | 需要 | 支持 | ✅ 满足 |
| **WDK** | 驱动开发工具包 | **未安装**（只有 SDK） | ❌ 需装 2~3 GB |
| **VS 驱动组件** | WDK 集成 | 无 | ❌ 需装 |
| **驱动签名** | 见下 | **CodeIntegrity=2 强制签名** | ❌ 最大门槛 |
| 测试模式 | 自签名需要 | 未开启 | ❌ 需重启 |

## 三、签名：真正的门槛

Windows 11 强制驱动签名（`CodeIntegrity=2`），三条路：

| 方式 | 成本 | 后果 |
|---|---|---|
| **A. 测试签名（自签）** | 免费 | 必须 `bcdedit /set testsigning on` + **重启**，桌面右下角永久"测试模式"水印，部分游戏反作弊会拒绝运行 |
| **B. EV 代码签名证书** | ￥2000~5000/年 | 还要走微软 **Attestation 签名**（Partner Center 审核），周期 1~2 周 |
| **C. 用别人的已签名驱动** | 免费 | 用 VDD，功能不可定制 |

## 四、三条实施路径

### 路径 1：装现成 VDD（推荐）

```powershell
winget install --id=VirtualDrivers.Virtual-Display-Driver -e
```

| 项 | 情况 |
|---|---|
| 工作量 | **1 条命令** |
| 签名 | 已是微软签名，**不用测试模式** |
| 效果 | 系统多一块虚拟显示器，可拖窗口进去 |
| 定制 | 不能改（但支持自定义分辨率/刷新率/EDID） |
| 风险 | 与重大 GPU 驱动更新可能冲突，极端情况开机黑屏（安全模式可卸载） |

### 路径 2：改微软 IddSampleDriver

微软官方示例：`Windows-driver-samples/video/IndirectDisplay/IddSampleDriver`

| 项 | 情况 |
|---|---|
| 工作量 | 装 WDK + 改 ~2000 行 C++ + 编译 + 签名，**2~5 天** |
| 签名 | **仍需自签 → 测试模式水印**，除非买 EV 证书 |
| 收益 | 可定制分辨率列表、EDID、多显示器、专用传输通道 |

### 路径 3：从零写 IDD

| 项 | 情况 |
|---|---|
| 工作量 | **2~4 周**（含调试内核态 DWM 交互、SwapChain 管理、崩溃恢复） |
| 风险 | 内核崩溃 = 蓝屏，调试要双机 |
| 收益 | 相对路径 2 几乎没有额外收益 |

## 五、关键判断：值不值得

**驱动级解决的是"系统认为多了一块屏"，不解决"画面更快"**。

我们的硬约束是：

| 环节 | 限制 |
|---|---|
| 屏幕解码 | 设备固件只认 **JPEG**，换不了 H.264 |
| 传输 | **HID 中断传输，实测上限 ~20 fps** |
| 单帧 | 8~20 KB / 9~20 个 1025 字节包 |

**即使做了驱动级虚拟屏，捕获后仍然要走同一条 HID 通道 → 帧率画质一点都不会变。**

驱动级带来的**唯一真实收益**是：能把任意窗口"拖"到虚拟屏上（而不是从下拉框里选）。

而这个体验，**装 VDD 就完全能拿到，零开发成本**。

## 六、建议：混合方案

| 步骤 | 做什么 | 成本 |
|---|---|---|
| 1 | 装 VDD（winget 一条命令） | 5 分钟 |
| 2 | 我的软件自动识别虚拟屏（名称含 Virtual / 分辨率异常） | 已支持枚举，加个标注 |
| 3 | 加「一键把当前窗口移到虚拟屏」辅助功能 | 用 `SetWindowPos` + 枚举显示器，~100 行 |
| 4 | 虚拟屏内容由 DXGI 捕获推 HID | 已实现 |

这样能拿到"拖窗口"体验的 **90%**，成本接近零，且不碰内核、不碰签名、不会蓝屏。

## 七、什么情况下才真的需要自己写驱动

只有这些场景值得：

1. 要把画面**直接注入驱动**（不经 DWM 合成），追求 <5ms 延迟
2. 要做**专用传输协议**（比如 USB 直连设备，绕过 HID 20fps 限制）
3. 要**商用分发**（那就必须买 EV 证书 + 微软签名，因为用户不可能都开测试模式）
4. 需要**非标准显示器行为**（自定义时序、特殊色彩空间）

自用 + 目标是散热器小屏，这四条都不成立。
